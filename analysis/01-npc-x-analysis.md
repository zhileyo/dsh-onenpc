# npc-x 项目分析（移植源调研）

> 调研对象：`D:\Projects\npc-x`（三省六部 · 无人值守多 NPC 协作体系 · i.o/x，CNB 平台版）
> 目的：为把它移植成 DeepSeekRuntime（DSH）插件 `dsh-onenpc` 做源侧摸底。
> 配套设计见 [02-design.md](./02-design.md)。

---

## 一、项目定位

npc-x **不是传统软件，而是一套"配置 + 流水线 + 文档"三件套**，它的运行时就是 CNB（cnb.cool）平台本身：

| 文件 | 作用 | 体量 |
|---|---|---|
| `AGENTS.md` | 体系总纲：组织架构、公文协议、冲突仲裁、多轮状态机、DoD、红线、学习进化、体量治理 | ~620 行 / 15 节 |
| `.cnb/settings.yml` | 12 个 NPC 角色注册（每角色一段人格化 prompt，Anthropic XML 分节风格） | 中书令/门下侍中/尚书令/六部（吏户礼兵刑工）/太史令/御史台/翰林学士 |
| `.cnb.yml` | 触发流水线：事件 → `npc:go` 按 `NPC_ROLE` 从 settings 解析角色 prompt 执行 | **512KB**，大量内嵌脚本（质量门/熔断器/心跳巡检/自愈环） |

**平台机制即运行时**（这是移植时最大的认知转换点）：

- **Issue = 台账 + 看板**：分层台账（1 个总纲 Issue 管对话交付 + N 个单任务台账 Issue 管干活）
- **评论 = 公文总线**：诏令 / 回奏 / 封驳 三式结构化 markdown
- **@提及 = 事件触发**（issue.comment@npc），**api_trigger = 调兵令**（链式拉起下游，不吃评论配额）
- **PR + CI = 交付载体与质量门**（刑部审查 → 门下复审 → gate 脚本 → 自动合并 → failStages 自愈）
- **crontab = 心跳**（日间 `*/30 7-23` + 夜间 `0 0-6`，十维巡检：可合并 PR、断链补触发、督办、预算、撞线等）

## 二、核心机制清单（要搬的制度内核）

1. **角色体系**（12 角色 + 平台内置 CodeBuddy）：中书令唯一入口/唯一合并权；门下侍中独立评审一票否决；尚书令执行总管；六部分工；外协（太史令智库/御史台稽核/翰林学士规划）。
2. **任务判级**：S0微小/S1小/M中/L大/XL超大，按「规模×复杂度×风险×并行需求」高水位取档，**最小可用编成**，质量门永不降级。
3. **公文协议**：诏令（目标/改动范围/前置依赖/验收标准/禁止事项 + 本轮编辑预算 b_t）、回奏（状态/改动/验证/关联/遗留）、封驳（结论/逐条理由/要求）。
4. **多轮状态机**（§8）：立项→拆解→派单→初审(刑部)→复审(门下)→自动合并→部署→验收→（未达标回拆解）→交付；停止条件=验收全满足/封驳计数达3换方案/触红线。
5. **护栏（全部应代码化，不靠提示词）**：封驳计数 N/3（断路器，换方案归零）、自愈轮次 M/3、token 预算硬顶（常规档 maxTurns 500 / 64k tokens）、改动范围白名单、完成门槛（验收未清不许 Done）。
6. **学习进化**：案例库（casebook/ 六分册）+【经验卡】格式（场景/坑点/解法/**适用条件**/来源/建议并入）+ 开工先回放（Replay-First）+ 踩坑必沉淀（Lessons-Locked）。
7. **能力包**：`.codebuddy/skills/` 13 个 SKILL.md（task-triage 判级、dispatch-agent 派单、orchestration-ledger 台账、plan-gate-review 评审等），按需加载不常驻。

## 三、移植判定表

| npc-x 组件 | 判定 | 理由 / 对位 |
|---|---|---|
| 12 角色 prompt（settings.yml） | **搬（精简）** | 提炼成人设+职掌+公文格式，**禁注入完整总纲**（npc-x 自己 §6.6-C 就禁止全量注入，防 token 失控） |
| 判级 / 编成路由（task-triage） | **搬** | dispatch 层逻辑，代码化 |
| 公文三式 + 多轮状态机 | **搬（结构化）** | 评论里的 markdown → task 对象的结构化数组，UI 可视化 |
| 质量门（刑部/门下评审） | **搬（换载体）** | PR+CI → 子会话产出 + `ctx.llm.stream` 独立评审轮（dsh-edict-demo pipeline.js 已验证） |
| 封驳计数/预算/完成门槛等护栏 | **搬（进代码）** | dsh-edict-demo 已示范：MAX_REVIEW_ROUNDS、预算闸门、assertCompletable 全在代码 |
| 案例库 + 经验卡 + 能力包 | **搬（换载体）** | `$DSH_HOME` 下 md 案例库 + DSH skills 体系（`.dsh/skills`） |
| 分层台账 Issue | **换载体** | 插件 `state.json`（任务记录/公文流/审计），看板 UI 替代 Issue 视图 |
| 评论配额红线 + 滚动续接 | **不搬** | DSH 无评论配额，问题消失 |
| api_trigger 三态判据（态A/B/C） | **不搬** | 调度在插件进程内，无跨根组织问题 |
| watchdog / keeper / spark（跨根保活） | **不搬** | 同上，CNB 平台特有问题的解法 |
| crontab 心跳十维巡检 | **缩编搬** | `ctx.schedule` 定时督办/断链扫（边界：DSH 进程退出即停，UI 如实标注） |
| 御史台稽核 | **可选后置** | 可做成审计模式（扫越范围/跳门），非第一版必需 |
| RAG 检索（kb-query.sh） | **可选后置** | 案例库初期直接整册读（分册小），量大再考虑 |

## 四、与 dsh-edict-demo（edict 移植版）的关系

- dsh-edict-demo 移植的是 **edict**（`cft0808/edict`，同为三省六部制、封建王朝风格，12 官员/12 态状态机/旨意看板）；npc-x 是**同题材的 CNB 平台工程化版本**，制度更重（判级/分层台账/预算硬顶/学习进化/巡检心跳）。
- **dsh-edict-demo 骨架整体可复用**（同作者、MIT、同构）：两半侧架构、iframe 单份 UI、长轮询、store、审计、agents.create 办差、pipeline 制度四环、预算闸门。
- dsh-onenpc 的差异化价值：**① 对话框 @npc 直达**（edict 是看板下旨）；**② npc-x 的判级与编成制度**；**③ 流程节点可视化**（拆解/派单/施工/初审/复审/合并/验收的节点图与产物）；**④ npc-x 的护栏全套代码化**（封驳计数/编辑预算/验收清单权责）。

> 结论：**dsh-onenpc = dsh-edict-demo 骨架 + npc-x 制度内核 + @npc 对话入口 + 流程节点详情页**。
